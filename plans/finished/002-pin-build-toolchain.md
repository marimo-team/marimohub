## Why this matters

The entire build/test/typecheck toolchain is pinned to **floating `latest`
tags** in the pnpm catalog. Two installs on different days — or a fresh CI run —
can resolve to _different_ compiler/bundler/test-runner versions, silently
changing build output, type-checking strictness, and test behavior. This is the
classic non-reproducible-build and supply-chain-exposure footgun, and it
directly undermines plan 001's CI gate (CI would not be testing a fixed
toolchain). The lockfile currently resolves all three to `0.1.24`; this plan
pins the catalog to that exact version so installs are deterministic.

## Steps

### Step 1: Read the exact resolved version from the lockfile

Run `grep -m1 "  vite-plus@" pnpm-lock.yaml` and `grep -m1 "@voidzero-dev/vite-plus-core@" pnpm-lock.yaml`.
Record the exact version (expected `0.1.24`). Call it `<V>` below.

**Verify**: you have a concrete version string like `0.1.24`, not `latest`.

### Step 2: Replace the floating specifiers with the exact version

Edit `pnpm-workspace.yaml`, changing only these three catalog lines:

```yaml
vite: npm:@voidzero-dev/vite-plus-core@<V>
vitest: npm:@voidzero-dev/vite-plus-test@<V>
vite-plus: <V>
```

(Substitute the real `<V>` from Step 1, e.g. `0.1.24`.) Leave every other line,
the `overrides`, and `peerDependencyRules` exactly as they are.

**Verify**: `grep -c "latest" pnpm-workspace.yaml` → `0` for the toolchain
lines (i.e. no `@latest` / `: latest` remains in the catalog). Confirm by eye
that the three lines now carry the exact version.

### Step 3: Reconcile the lockfile without changing resolutions

Run `pnpm install --lockfile-only`. Because `<V>` equals what the lockfile
already resolved, this should produce **no change to resolved versions** (it may
re-stamp the specifier metadata).

**Verify**: `git diff pnpm-lock.yaml` shows only specifier-string changes (the
`specifier: npm:@voidzero-dev/...@latest` lines become `...@<V>`), and NO change
to any `version:` resolution line. If `pnpm install` wants to pull a _different_
resolved version, see STOP conditions.

### Step 4: Full verification

**Verify**: `pnpm install --frozen-lockfile && pnpm check && pnpm test && pnpm build` all exit 0.

## STOP conditions

Stop and report (do not improvise) if:

- The lockfile's resolved toolchain version is NOT a single clean version (e.g.
  multiple `vite-plus@` versions appear) — report what you found.
- `pnpm install --lockfile-only` wants to change a resolved `version:` (not just
  the specifier string) — that means `latest` had already drifted past the
  lockfile; do NOT accept the bump silently. Report the old and new versions so
  a human can decide whether to adopt the newer toolchain deliberately.
- `pnpm check`/`test`/`build` fails after pinning — report the failure.

## Maintenance notes

- Future toolchain upgrades become deliberate: bump `<V>` in the catalog, run

  the point of this plan is that the version only changes when a human changes
